## Execution Rules

1. Read the approved specification, plan, and relevant source files before starting a task.
2. Execute tasks only when every dependency is complete.
3. Work on one task per agent session unless an orchestrator explicitly assigns a disjoint parallel batch.
4. Workers own only the files listed by their task. They are not alone in the repository, must preserve unrelated edits, and must not revert other work.
5. The orchestrator updates checkboxes after verifying commits. Parallel workers do not edit this file.
6. Start behavior changes with the listed failing test or the closest user-observable test.
7. Stop and surface conflicts between the spec, plan, code, or observed macOS behavior.
8. Never cross an Ask First boundary without human approval.
9. Run the focused verification and every named verification profile before committing.
10. Use the task's lowercase conventional commit message without signatures or co-authors.

## Parallel Waves

These waves describe maximum safe parallelism. Dependencies on individual tasks still take precedence.

| Wave | Parallel work |
| --- | --- |
| 0 | P0 tasks are sequential because they share the project file. |
| 1 | Core contracts can split only after P0-08. Settings begins after stable identifiers exist. |
| 2 | P5 Keep Awake and P6 Copy Path may run in parallel after P4. |
| 3 | Independent Foundation actions may run in parallel after shared menu, shortcut, permission, and capture contracts settle. |
| 4 | P10, P11, and independent parts of P12 may run in parallel after P9. |
| 5 | P13 mutation engine is sequential because collision and recovery semantics are shared. |
| 6 | P14 event interception is sequential through the kill-switch checkpoint. |
| 7 | P15 audits may run in parallel with disjoint ownership after C3. |
